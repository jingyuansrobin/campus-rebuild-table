# MCRebuild V3 Architecture Draft

Status: Draft accepted from Day 1–2 product/architecture interview (2026-08-30)

## 1. Product thesis

MCRebuild is not another generic GIS-to-Minecraft generator.

Its purpose is to help university Minecraft clubs start and sustain campus reconstruction projects:

```text
real campus
  → automatic ~60-point base
  → club refinement in Minecraft
  → ~90-point campus work
```

Arnis owns the generic base-generation problem. MCRebuild owns campus semantics, project workflow, style/assets, and collaboration.

## 2. V3.0 user journey

```text
Open MCRebuild
  → search school
  → choose campus
  → CampusProject is created automatically
  → confirm/edit polygon boundary
  → optional orientation
  → choose generation scale (1.0–2.5 blocks per meter)
  → invoke Arnis
  → preview generated campus
  → open result in Minecraft
```

There is no object-by-object pre-generation review in V3.0. Everything within the confirmed boundary that the generation engine can handle is generated by default.

## 3. Runtime shape: Native Desktop + Headless Core

```text
Desktop thin shell ─┐
                    ├─→ Application Core
CLI / tests ────────┘        │
                             ├─→ Campus Core
                             └─→ Generation Service → Arnis Adapter → Arnis
```

Rules:

1. Desktop is the primary user-facing application.
2. Core use cases must be executable and testable without the GUI.
3. UI contains presentation state and event forwarding, not domain rules.
4. Arnis types and configuration must not leak into Campus Core.
5. CLI exists primarily for development, testing, diagnosis, and automation.

## 4. Core domain

### 4.1 CampusProject

`CampusProject` is the lifecycle/workspace container for one campus reconstruction effort.

It contains or references:

- stable project identity;
- school and campus identity;
- confirmed campus boundary;
- optional orientation;
- target Minecraft version;
- generation scale/profile;
- Reality Model;
- semantic Campus Objects;
- style/asset references;
- generation/output metadata;
- later: teams, tasks, versions and cloud synchronization metadata.

The user does not need to understand the concept before creating one. Selecting a campus creates the project automatically.

### 4.2 RealityModel

Represents the system's current understanding of the real campus.

Possible sources include OSM, AMap, Arnis-consumed geographic data, official sources, and later manual corrections.

Reality data and Minecraft creative decisions must remain conceptually separate.

### 4.3 CampusObject

The semantic unit that MCRebuild manages. Typical types include:

- Building
- Road
- Water
- Vegetation
- SportsFacility
- Plaza
- Landmark
- Region/other extensible types

V3 starts with one extensible `CampusObject` model plus an `ObjectType`, instead of immediately creating many independent domain hierarchies.

Minecraft blocks are generated representation/output, not the authoritative domain model.

### 4.4 Spatial hierarchy versus task hierarchy

Campus semantics may use containment/grouping such as:

```text
Campus → District/Region → CampusObject → optional semantic components
```

Do not force task assignment to match that tree. A task may target one object, many objects, a district, or a spatial selection.

## 5. Reality and project data: dual model

V3 keeps real-world source state separate from reconstruction intent:

```text
Reality Model
      +
Campus Project Model
      ↓
Generation / rendering
      ↓
Minecraft output
```

This separation allows future source refreshes without silently overwriting club decisions.

V3.0 does not implement sophisticated source reconciliation or conflict merging, but the model must not erase the distinction.

## 6. Generation layer

### 6.1 Arnis policy

For V3.0:

- Arnis is the only base generation engine.
- MCRebuild does not fork or enhance Arnis generation algorithms.
- MCRebuild accesses Arnis through a thin adapter boundary.
- Initial integration should prefer an external executable/process boundary if practical; library-level integration is only justified by a demonstrated need.

The abstraction is not a speculative multi-generator plugin platform. It is an isolation boundary so Arnis does not become the MCRebuild domain model.

### 6.2 Generation scale

Domain term: `blocks_per_meter`.

Allowed V3 range:

```text
1.0 ≤ blocks_per_meter ≤ 2.5
```

Recommended UI presets may include 1.0x, 1.5x, 2.0x and 2.5x. The domain stores the MCRebuild concept, not an Arnis-specific parameter name.

### 6.3 V3.0 generation settings

Keep visible settings minimal:

- Minecraft version;
- optional orientation;
- generation scale.

Do not expose a large GIS/procedural-generation control panel in V3.0.

## 7. Editor boundary

MCRebuild is a high-level semantic workbench, not a replacement for Minecraft/Axiom/WorldEdit.

Long-term MCRebuild editing concerns may include styles, asset references, object-level semantic settings and project organization.

Fine detail construction remains in Minecraft.

### V3.0 round-trip policy

V3.0 is one-way:

```text
MCRebuild → Minecraft
```

Minecraft edits are not imported back automatically. The domain should retain stable object/output references where cheap, so a later explicit round-trip feature remains possible, but V3.0 does not implement it.

## 8. Project storage: local-first

A CampusProject must be usable offline and remain owned by the user.

Logical project layout:

```text
<project>/
  project.json
  reality.json
  objects.json
  generated/
  cache/
```

Principles:

- authoritative project metadata should be human-readable and versionable where practical;
- cache is disposable/rebuildable;
- generated outputs are derived artifacts;
- SQLite may later be used for indexing, history or synchronization support, but should not be the only opaque source of truth for the project.

Cloud enhances collaboration; it does not own the local project.

## 9. Style system

Styles use hierarchical inheritance:

```text
Campus default style
  → District/Region override
    → CampusObject override
```

A CampusObject references a style. It should not duplicate all resolved Minecraft material rules into every object.

Long-term style definitions can contain material palettes and higher-level generation rules, but V3.0 should not rebuild a procedural building engine under the name of “styles”.

## 10. Asset system

Long-term Asset is a typed resource, potentially including:

- Style
- Schematic
- BuildingTemplate
- FacadePattern
- RoadStyle
- LandscapeAsset
- Landmark

V3.0 should implement only what is needed by the current vertical slices. Initial practical asset types are Style and Schematic; parameterized templates are deferred.

### Asset Hub

Long-term product direction is a central MCRebuild Asset Hub:

```text
Cloud-first discovery/distribution
            ↓
       local asset cache
            ↓
       CampusProject
```

Project storage remains local-first while asset discovery is cloud-first.

Do not build a full marketplace in V3.0. A mature rollout is:

1. define asset identity/metadata;
2. read-only curated asset catalog;
3. authenticated publishing/version management;
4. later community features.

Every publishable asset must carry author/source/license metadata from the beginning. Software licensing and asset licensing are separate concerns.

## 11. Collaboration system

MCRebuild collaboration focuses on organizing campus reconstruction work, not real-time Minecraft block editing.

### First collaboration capability

Tasks and construction status are attached to campus semantics/spatial targets.

Task flow:

```text
CampusObjects
  → TaskSuggestion
  → human merge/split/delete/confirm
  → Task
```

Tasks should support team assignment and optional individual ownership.

V3 task status should prefer discrete states such as:

```text
NotStarted → InProgress → Done
```

Do not require subjective manual percentages in the first version. Aggregate progress may be calculated from task state and later improved with weighting if real use demands it.

### Native membership direction

Long-term MCRebuild has first-class organizations/clubs, members, teams, roles and project membership. V3.0 must not require a complete account/auth system merely to ship local task management; cloud identity can arrive with collaboration milestones.

### Privacy model

CampusProject is a private workspace by default.

Public exposure is explicit publishing:

```text
Private Workspace
     ↓ explicit publish
Public Showcase / Asset Hub
```

Internal tasks, member data and unfinished project state must not become public automatically.

## 12. AI / Agent policy

AI / Agent features are explicitly outside the current V3 scope.

Do not add:

- LLM SDKs;
- agent frameworks;
- prompt infrastructure;
- RAG/vector databases;
- agent-only abstraction layers.

If an Agent is explored later, it should call normal application use cases rather than require a parallel architecture.

## 13. V3.0 explicit non-goals

V3.0 does not build:

- a second GIS-to-Minecraft generation engine;
- V2-style candidate review workflow;
- a full 3D/CAD editor;
- Minecraft bidirectional live synchronization;
- real-time collaborative project editing;
- a full asset marketplace;
- advanced procedural building templates;
- AI / Agent functionality.

## 14. Architecture quality principle

V3 optimizes for fast, reliable iteration by reducing the amount of software that must be correct.

Every new abstraction must demonstrate that it removes more complexity than it introduces. Mature V2 code is migrated only when it directly supports a V3 user journey or removes proven implementation risk.
