# V3 v0.1 Vertical Slice — Local CampusProject

## Goal

Prove the new architecture with the smallest useful headless workflow before migrating GUI/GIS code.

The first slice must allow a developer or test to create a valid local `CampusProject` without any desktop UI or Arnis integration.

## User-visible-equivalent flow

```text
school + campus + generation scale
        ↓
Application Core
        ↓
CampusProject validation
        ↓
local project directory
```

This is intentionally smaller than the final V3.0 user journey.

## Required output

Given:

- project directory;
- school name;
- campus name;
- scale in the inclusive range 1.0–2.5 blocks/m;

create:

```text
<project>/
  project.json
  reality.json
  objects.json
  generated/
  cache/
```

`project.json` is the authoritative initial project metadata.

## Architecture exercised

```text
apps/cli
   ↓
app-core
   ↓
campus-core
```

`arnis-adapter` is introduced only as a boundary crate in this milestone; generation is not yet invoked.

## Acceptance criteria

1. Workspace builds with stable Rust.
2. Campus Core rejects generation scale below 1.0 or above 2.5.
3. Application Core creates the full local project layout.
4. Re-running create against a non-empty existing project directory fails instead of silently overwriting data.
5. `project.json` can be parsed back into the same domain model.
6. Core behavior has unit tests without launching a GUI.
7. No Slint, WebView, GIS, cloud, AI, or Arnis runtime dependency is required to run these tests.

## Deferred vertical slices

### v0.2 — Campus search + automatic project creation

Port only the smallest proven school/campus search capability required from V2.

### v0.3 — Polygon boundary

Add map boundary confirmation/editing and persist it in the project model.

### v0.4 — Arnis process adapter

Translate MCRebuild generation settings into an Arnis invocation and capture output/errors.

### v0.5 — Preview + open result

Preview generated campus and hand off to Minecraft workflow.

Only after this end-to-end path is stable should V3.1 style/assets/tasks be pulled forward.

## Quality policy

For each vertical slice:

- domain validation tests first;
- one application-level happy-path test;
- one important destructive/error-path test;
- minimal CI: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`;
- do not add architecture tooling until a recurring failure proves it is needed.
