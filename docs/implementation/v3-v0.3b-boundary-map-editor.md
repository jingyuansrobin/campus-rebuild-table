# V3 v0.3b — Boundary Map Editor

## Goal

Turn the v0.3a authoritative WGS-84 polygon into the first user-editable desktop vertical slice without migrating V2's large boundary page or its Slint + embedded child WebView complexity.

```text
CampusProject + RealityModel
        ↓ app-core
BoundaryEditorContext
        ↓
gaode-map
  WGS-84 → GCJ-02 display
  small HTML / JS map page
  small IPC protocol
        ↓
Windows winit + Wry shell
        ↓ submit_boundary
GCJ-02 → WGS-84
        ↓ app-core
CampusBoundary validation
        ↓
project.json atomic save
```

## V2 audit decision

### Keep as experience

- AMap is useful for the user-facing China campus map canvas.
- `AMap.PolygonEditor` is appropriate for moving polygon vertices.
- Map JavaScript should act as a drawing/display adapter rather than project business logic.
- Existing confirmed boundary should be shown and editable when reopening a project.

### Rewrite

- CRS conversion is explicit at the adapter boundary: Core is WGS-84, AMap display is GCJ-02.
- IPC is reduced to `ready`, `cancel`, `submit_boundary`.
- Core validation receives geographic coordinates, not UI event/state-machine types.
- Desktop obtains its view context from `app-core`; it does not read project JSON itself.
- The desktop shell is one native winit window with one Wry WebView for this slice.

### Do not migrate

- the ~57 KB V2 generated boundary HTML/JS page as a unit;
- Slint + embedded Wry child-window composition for the current slice;
- raw-window-handle bridge and Windows child-window focus/subclass workarounds;
- OSM automatic candidate selection/review inside the boundary page;
- orientation mode in the same page;
- search or project creation logic inside the map.

## Why a Wry-only desktop shell now

The product decision remains **Native Desktop + Headless Core + Thin GUI**. It does not require Slint specifically.

For v0.3b, using one native window with Wry gives the shortest path to prove the campus boundary workflow because the map itself already requires browser rendering. Reintroducing a separate native UI toolkit around that WebView would add window embedding, focus, sizing and event-bridge failure modes before those capabilities provide user value.

This is a reversible shell decision. `campus-core`, `app-core` and `gaode-map` do not depend on the final desktop composition strategy.

## Adapter contract

`gaode-map` owns:

- AMap JS page generation;
- safe bootstrap data embedding;
- WGS-84 → GCJ-02 conversion for display;
- GCJ-02 → WGS-84 conversion for submitted map coordinates;
- parsing the three IPC event types.

It does not own:

- project persistence;
- final polygon validity;
- Arnis generation;
- campus search;
- project identity/lifecycle.

## Desktop contract

The development executable is currently:

```text
mcrebuild-desktop <project_dir>
```

It requires:

```text
AMAP_JS_KEY
AMAP_JS_SECURITY_CODE
```

The project must contain a geographic anchor produced by a real campus selection. A manual project with no source anchor fails explicitly rather than inventing a location.

On `submit_boundary`, Desktop delegates to `app-core::set_project_boundary`. Domain rejection is returned to the page as a user-visible status instead of allowing JavaScript to decide whether the polygon is valid.

## Quality gates

PR CI contains two distinct gates:

1. Ubuntu workspace: rustfmt + Clippy + all unit tests.
2. Windows Desktop: compile/Clippy the real Windows-only Wry/winit path.

This prevents a non-Windows `main(){}` stub from falsely proving desktop compatibility.

## What CI proves

- Rust types and project boundaries compile on the pinned toolchain;
- the Windows Wry/winit integration compiles;
- CRS and IPC adapter unit tests pass without live services;
- project loading and boundary persistence tests pass;
- no live AMap request is necessary in CI.

## What CI does not prove yet

A successful build is **not** an end-to-end desktop acceptance test. Before v0.3b is treated as user-validated, run one real Windows smoke test with a configured AMap JS key/security code and confirm:

1. WebView2 opens the local custom-protocol page;
2. AMap JS SDK accepts the page origin/key configuration;
3. map tiles load and center on the selected campus;
4. a polygon can be drawn and edited;
5. invalid polygons are rejected with feedback;
6. valid polygons persist and reappear after reopening the project.

If the AMap console/domain policy rejects the custom protocol origin, change only the desktop/map serving boundary; do not weaken the WGS-84 domain model to work around it.

## Known deliberate debt

These are acceptable for the development slice but should not quietly become release-quality behavior:

- window/WebView construction currently uses `expect` for fatal startup failures;
- best-effort UI feedback ignores `evaluate_script` and event-proxy send failures;
- GCJ-02 conversion code currently exists independently in search and map adapters; consolidate only when shared maintenance pain appears;
- Desktop currently exposes a project-directory CLI argument instead of recent-project/open-project UX;
- the current shell UI is mostly WebView content and has not yet established the final visual system;
- no native automated visual/E2E test exists yet.

## Deferred

- automatic OSM campus-boundary discovery;
- optional orientation editing;
- scale settings UI;
- Arnis invocation and progress;
- polygon mask/crop after Arnis generation;
- recent-project/home screen;
- asset/style editing.

The next product-critical slice after v0.3b should favor **Arnis generation integration** over polishing optional orientation, because the MVP promise is school → boundary → generated 60-point campus.
