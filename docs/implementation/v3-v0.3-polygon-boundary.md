# V3 v0.3 — Authoritative Polygon Boundary

## Goal

Introduce a typed, provider-neutral campus reconstruction boundary before building the desktop map editor.

```text
CampusCandidate (normalized to WGS-84)
        ↓
CampusProject
        ↓
CampusBoundary (authoritative polygon, WGS-84)
        ↓
Derived rectangular BBOX for Arnis transport only
```

The project boundary is a product/domain concept. The Arnis bounding box is an adapter limitation and must never replace it in project data.

## V2 audit

### Keep as experience

- at least three effective vertices;
- reject degenerate/tiny polygons;
- reject self-intersection;
- tolerate an explicitly repeated closing vertex by normalizing it away;
- map UI should behave as a canvas/bridge, not own project business rules;
- preserve an anchor to center the future map editor.

### Rewrite

- `Boundary` must not store untyped `serde_json::Value` coordinates;
- boundary validation operates on geographic domain points, not a UI `Vertex` type;
- project persistence owns the confirmed boundary directly;
- coordinate system identity must be explicit in types and adapter boundaries;
- map editor protocol must be smaller than the V2 all-in-one HTML/JS page.

### Drop from the V3 core

- V2 `BoundaryDrawer` pointer-event state machine;
- Web Mercator → plane → Minecraft block conversion inside boundary editing;
- the 57 KB generated boundary HTML/JS page as a migration unit;
- orientation behavior from this slice (orientation remains optional and will be reintroduced separately).

## Coordinate policy

All provider-neutral geographic coordinates inside `campus-core` are WGS-84.

- AMap/高德 adapter input/output uses GCJ-02 inside China and converts to WGS-84 before returning domain data.
- Future AMap map rendering converts WGS-84 → GCJ-02 only at the display adapter boundary.
- Arnis receives WGS-84 latitude/longitude.

This prevents anonymous `lon/lat` values from silently crossing coordinate systems.

## Schema transition

v0.3 makes the coordinate-system contract explicit.

- `project.json` remains backward-readable from the v0.2 development schema because `boundary` is optional; once the boundary is updated it is saved at the current project schema version.
- `reality.json` v0.2 is **not** silently accepted, because its AMap anchor values were stored in GCJ-02 while v0.3 core coordinates are WGS-84. Old development Reality data must be rebuilt from the provider rather than misinterpreted.

Pre-1.0 project files are still development artifacts, but incompatible coordinate semantics must fail explicitly instead of producing a geographically shifted project.

## Boundary model

`CampusBoundary` stores one simple polygon exterior ring for V3.0.

Rules:

1. at least three effective vertices;
2. a repeated last vertex equal to the first is removed during normalization;
3. consecutive duplicate vertices are rejected;
4. self-intersections are rejected;
5. near-zero/tiny polygons are rejected;
6. holes and MultiPolygon are deferred until a real campus case proves they are required;
7. winding direction is preserved but currently has no user-visible meaning; semantic winding normalization is deferred until a real consumer requires it.

The first implementation deliberately supports a simple polygon only. Supporting MultiPolygon because V2 once exposed GeoJSON would be speculative complexity.

## Arnis limitation and product truth

As of the current Arnis CLI/GUI workflow, generation selection is rectangular and the CLI accepts `--bbox=min_lat,min_lng,max_lat,max_lng`.

Therefore:

- `CampusBoundary::bounding_box()` may derive a rectangle for the Arnis adapter;
- that rectangle is not persisted as the authoritative campus boundary;
- generating the rectangle alone does **not** count as delivering the custom-polygon product promise;
- before V3.0 can claim arbitrary-shape generation, MCRebuild must either apply a post-generation polygon mask/crop or adopt a deeper Arnis integration that honors the polygon.

Current preference: keep Arnis unmodified and add a separate MCRebuild mask stage later, unless implementation evidence shows that route is more expensive than library-level integration.

## v0.3a executable slice

Before any desktop map UI:

1. `CampusCandidate` anchor is normalized from AMap GCJ-02 to WGS-84;
2. `CampusBoundary` validates and normalizes a WGS-84 polygon;
3. `CampusProject` can persist an optional authoritative boundary;
4. Application Core can load a project and set/replace its boundary atomically;
5. CLI can set a polygon from coordinate pairs for deterministic development testing;
6. a WGS-84 rectangular BBOX can be derived for the future Arnis adapter.

## Deferred to v0.3b

- AMap WebView polygon drawing/editing;
- WGS-84 ↔ GCJ-02 map bridge protocol;
- automatic boundary discovery from OSM;
- visual area-size feedback;
- optional orientation UI.

## Acceptance criteria

- invalid coordinate values cannot enter the domain;
- a bow-tie/self-intersecting polygon is rejected;
- a valid campus-scale polygon round-trips through `project.json`;
- an explicitly closed ring is normalized to an open stored ring;
- the derived BBOX contains every boundary vertex;
- replacing a boundary never rewrites unrelated RealityModel/Object data;
- AMap search tests prove that returned domain anchors are WGS-84, not raw GCJ-02;
- v0.2 Reality data is rejected rather than silently interpreted in the wrong CRS;
- CI makes no live AMap or Arnis calls.
